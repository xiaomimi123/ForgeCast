# 文案真实感修复设计

## 背景

用户反馈生成的视频/文案"始终不满意"，追问后定位到三个具体问题（用户原话确认"以上都是"）：

1. **钩子/角度不对**：痛点/卖点角度跟目标受众实际需求对不上。
2. **语气 AI 味重**：能看出是 AI 写的，不像真人小红书/抖音口吻。
3. **内容不真实/空洞**：编数据、编经历、水文。

## 根因（Explore 结果）

- `templates/prompts/analysis.md` 要求 LLM 只凭 README+目录树就编出"部署价9800元""每年浪费5-15万"这类它无从知道的具体数字，下游文案原样照抄，还在此基础上加编第一人称经历（"我也是踩了两年坑才反应过来"）。
- `templates/prompts/copy-{hook}.md` 的"示例骨架"里直接写着 `花X天`、`成本不到XXX` 这种占位符，等于在教 LLM 造数字。
- 所有格式说明文件（`_format.md`、`copy-*.md`）只有违禁词/合规红线，没有"真实感"红线——视频那边有这条规则（演示段必须真实录屏），文案这边从没写过。
- 选题库（`viral_notes`/`topic_patterns`）机制代码上是通的，但数据库里 0 行，从未真正影响过一次生成——角度选择完全靠 4 个抽象钩子公式，没有真实爆款参照。
- `projects` 表关联的 `candidates` 表其实有真实的 `stars`/`license`/`tech_stack`，但分析报告生成时完全没用上这些，纯靠 LLM 凭 README 猜。

## 设计（用户已确认的取舍）

**定价不用真实报价，只用定性描述**——用户明确不想在文案/分析报告里出现具体价格数字（即便是自己配置的真实 `price_deploy`/`price_custom`），全部改成定性表达。

**人物经历允许模糊化口吻，但不能带具体细节**——"我""身边同行"这类第一人称/群体口吻可以保留，但不能编具体时间/次数（"两年""三轮"这种）。

### A. `templates/prompts/analysis.md`：去掉编数字的要求，喂真实客观事实

- 「目标买家画像」的"每年花多少钱"、「痛点清单」的"现状成本（时间/钱）"、「定价建议」整节——把 prompt 里要求给具体数字的措辞，改成明确要求定性表达（"明显更省时间""比外包/SaaS 方案划算不少"），不出现任何数字。
- 「定价建议」这节标题不删（下游 `copy-infogap.md` 会引用"对比市面 SaaS 年费"这个方向），但内容改成纯定性对比，不出现价格数字。
- prompt 输入新增一段【项目客观事实】，把 `candidates` 表的 `stars`/`license`/`tech_stack` 传进去（`packages/analyst/src/analyze.ts` 现在只传 README+tree，改成 join `candidates` 表一并传入），让 LLM 有真材料可写，而不是纯靠 README 联想编数字。
- `packages/analyst/src/validate.ts` 的结构校验（7 段）不变——只改每段"要求什么内容"的措辞，不改段落结构，不影响下游 `assemble.ts`/`copy-*.md` 对 analysis.md 的引用方式。

### B. 文案提示词：加真实感红线 + 去掉占位符诱导

- `templates/prompts/_format.md` 末尾【违禁词红线】之后新增【真实感红线】：
  - 不得编造具体数字（工作日数、周数、金额、百分比、轮次等），没有真实数据支撑时一律用定性表达
  - 允许"我""身边同行/同事"等模糊人称口吻，但不能带具体时间点/次数细节（不能说"两年""改了三轮"这种编造细节）
  - 所有具体事实（功能、场景、痛点）必须能在【商业化分析报告】里找到出处，不得自创分析报告没提过的痛点/功能——分析报告本身在 A 步已经喂了真实客观事实（star 数/协议/技术栈），真实信息是从这一层往下游传递的，文案生成这一步不直接接触 candidates 表
- 四个 `copy-{hook}.md` 的"示例骨架"去掉 `X` 占位符字面量，改成不含数字的结构描述（例如 `copy-infogap.md` 的"老板花X万买的，成本其实只要X"改成"老板花大价钱外包的，这套自己部署成本低很多"）。
- `assemble.ts` 的 prompt 组装顺序不变，只是 `formatSpec` 内容变长（多了真实感红线段）；`AssembleInput`/`assemblePrompt` 签名不变。

### C. 选题库填真实数据（人工辅助抓取）

- 复用已有的选题库机制（`packages/topics`，`topics add-source`/`import-notes`/`extract` CLI，或对应的 Web API）——这套代码已经在之前的会话里做好并验证过，只是数据库是空的。
- 本轮由用户提供 2-3 个同赛道（开源改造/外包接单/程序员副业类）小红书或抖音账号，Claude 用浏览器工具人工查看这些账号的爆款笔记（标题、大致互动量），通过现有 CLI/API 把笔记数据和账号信息录入 `topic_sources`/`viral_notes`，再跑 `extract` 生成 `topic_patterns`。
- 严格遵循这套机制原有的设计约束（本项目此前已确认）：**不做自动化定时爬虫，不做二维码登录/cookie 持久化**，全程是"人看人录入"，不新增任何抓取代码。

## 不做的事

- 不改选题库的代码机制本身（`packages/topics` 已完整，本轮只是把数据填进去）。
- 不把真实 `price_deploy`/`price_custom` 塞进 prompt——用户明确要求只用定性描述。
- 不改视频模板/生成逻辑——这轮只解决"文案内容方向不对"，视觉层的问题（画面简陋）留到确认这轮文案质量提升后再看是否需要继续加模板。
- 不改 `packages/analyst/src/validate.ts` 的段落结构校验规则。
- 不新增数据库表/字段。

## 验证

1. 用改造后的 prompt 对 ant-design-pro 重新跑一次 `analyze` + `copy`（live 模式），人工核对：analysis.md 和文案里不再出现具体数字（工作日/周数/金额/百分比），第一人称经历不带具体时间/次数细节。
2. 选题库导入至少 1 个账号的真实笔记数据后，重新生成一次文案，确认【选题风格参考】区块在 prompt 里真的被填充（不再是空字符串）。
3. `pnpm test` 回归，重点看 `packages/analyst`、`packages/copywriter` 现有测试是否因 prompt 文案改动需要同步更新断言（测试大多是 mock 模式，走 fixture，不直接断言 prompt 文本，预期改动很小）。
